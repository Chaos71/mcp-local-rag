## Context

mcp-local-rag использует переменные окружения для конфигурации (DB_PATH, MODEL_NAME, BASE_DIR и т.д.). В настоящее время пользователи должны вручную устанавливать эти переменные через shell, docker-compose, systemd или другие механизмы. Файл `.env.example` существует как документация, но не загружается автоматически.

**Текущее состояние:**
- Переменные читаются напрямую из `process.env` в точках входа
- Нет механизма автоматической загрузки `.env`
- `.env.example` — только шаблон-документация

## Goals / Non-Goals

**Goals:**
- Автоматическая загрузка `.env` из текущей рабочей директории при старте
- Безопасное поведение: внешние переменные сохраняют приоритет
- Минимальные зависимости (предпочтительно встроенный парсер)
- Предупреждения о неизвестных переменных из `.env.example`

**Non-Goals:**
- Поддержка нескольких `.env` файлов (.env.local, .env.production и т.д.)
- Шифрование или защита `.env` файла
- Валидация типов переменных
- Поддержка переменных окружения secrets-менеджеров (Vault, AWS Secrets Manager)

## Decisions

### Решение 1: Встроенный парсер вместо dotenv
**Выбор:** Использовать встроенный парсер `.env` вместо пакета `dotenv`

**Альтернативы рассмотрены:**
- `dotenv` (npm) — популярный, но добавляет ~15 KB зависимостей
- `dotenv-expand` — поддерживает переменные внутри `.env`, но усложняет
- Встроенный парсер — ноль дополнительных зависимостей, полный контроль

**Рациона:** mcp-local-rag стремится к минимальным зависимостям (Transformers.js уже тяжёлый). Формат `.env` прост: `KEY=VALUE`, комментарии `#`, пустые строки. Встроенный парсер будет ~50 строк кода.

### Решение 2: Точка входа — до роутинга
**Выбор:** Загружать `.env` в начале `src/index.ts`, до любого другого импорта

**Рациона:** Гарантирует, что все последующие модули (`cli-main.ts`, `server-main.ts`) получают переменные из `.env`. Не влияет на поведение — `process.env` глобален.

### Решение 3: Не перезаписывать существующие переменные
**Выбор:** `process.env[key] = value` только если ключ не установлен

**Рациона:** Пользователи могут иметь переменные в shell, docker-compose, CI/CD. Внешняя среда должна иметь приоритет над `.env`.

### Решение 4: Предупреждения о неизвестных переменных
**Выбор:** При загрузке `.env.example` проверять, какие переменные не установлены, и выводить предупреждение

**Рациона:** Помогает новым пользователям понять, какие переменные нужно настроить. Не блокирует запуск.

## Risks / Trade-offs

| Риск | Митигация |
|------|-----------|
| `.env` содержит секреты в git | Добавить `.env` в `.gitignore` автоматически при первом запуске |
| Парсер не поддерживает все edge-case форматирования | Поддерживать базовый формат (99% use-cases); сложные случаи — пользователь настраивает через shell |
| Конфликт имён переменных между проектами | Каждый проект имеет свой `.env`; нет глобального состояния |

## Migration Plan

Не требуется — это добавление новой функциональности без изменения существующего поведения.
