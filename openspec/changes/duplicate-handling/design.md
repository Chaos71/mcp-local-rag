## Context

Проект использует LanceDB (file-based) и PostgreSQL (pgvector) как бэкенды для хранения векторных чанков. Текущий механизм реингеста: `deleteChunks(filePath) → insertChunks(chunks)` — полностью заменяет старую версию. Нет отслеживания, что файл уже существует в индексе, и нет детекции на уровне содержимого.

**Текущее состояние:**
- `VectorStore.deleteChunks()` — удаляет все чанки по пути к файлу
- `VectorStore.insertChunks()` — вставляет новые чанки
- `IngestResult` — содержит `filePath`, `chunkCount`, `timestamp`, `fileTitle`
- `DuplicateStore` — **не существует**

**Ограничения:**
- Нет сравнения содержимого — пользователь может загрузить один файл 10 раз
- Нет связи между разными версиями одного документа
- Нет способа найти и удалить «призрачные» дубликаты

## Goals / Non-Goals

**Goals:**
- Детекция идентичных документов по SHA-256 хешу содержимого
- «Мягкое удаление» старых версий при реингесте изменённого файла
- Отслеживание цепочек дубликатов для пакетной очистки
- Прозрачная интеграция в существующий ingest pipeline

**Non-Goals:**
- Автоматическое удаление дубликатов без подтверждения пользователя
- Сравнение документов по семантической близости (только точное совпадение)
- Миграция существующих данных в новую схему
- Поддержка сравнения разных форматов (PDF vs TXT с одинаковым текстом)

## Decisions

### Решение 1: Хранение метаданных дубликатов

**Выбор:** Отдельная таблица `duplicates` в векторной БД

**Альтернативы:**
1. Отдельный JSON-файл `duplicates.json` — не работает с PostgreSQL-бэкендом, усложняет синхронизацию
2. Расширить таблицу `chunks` полем `duplicateOf` — нарушает принцип единой ответственности, усложняет запросы

**Обоснование:** Таблица `duplicates` хранит только метаданные (хеш, путь, связь). Векторные чанки остаются в основной таблице. Это соответствует архитектуре PostgreSQL-бэкенда, где уже есть отдельная таблица `files`.

### Решение 2: Режимы обработки дубликатов

**Выбор:** Три режима через переменную `DUPLICATE_MODE`:
- `skip` — пропустить загрузку, вернуть предупреждение (по умолчанию)
- `update` — обновить существующий документ (текущее поведение)
- `track` — сохранить оба экземпляра с пометкой о дубликате

**Альтернативы:**
1. Только два режима (skip/update) — не покрывает сценарий отслеживания
2. Всегда track + ручная очистка — неудобно для пользователя

**Обоснование:** Три режима покрывают все сценарии: предотвращение дублирования, обновление и аудит.

### Решение 3: Хеш содержимого

**Выбор:** SHA-256 хеш полного содержимого файла

**Альтернативы:**
1. MD5 — быстрее, но слабее криптографически
2. Хеш размера + времени модификации — неточный, не обнаруживает изменения содержимого

**Обоснование:** SHA-256 обеспечивает надёжное обнаружение изменений. Вычисление быстрое для документов до 100 МБ (ограничение `MAX_FILE_SIZE`).

### Решение 4: Мягкое удаление

**Выбор:** Пометить чанки как `status: 'deprecated'` в таблице `chunks`, не удаляя физически

**Альтернативы:**
1. Удалить чанки из таблицы `chunks` — теряется история
2. Переместить в отдельную таблицу `deprecated_chunks` — усложняет запросы

**Обоснование:** Поле `status` в таблице `chunks` позволяет фильтровать устаревшие чанки при поиске без изменения схемы. Для PostgreSQL-бэкенда это отдельное поле в таблице `chunks`.

### Решение 5: Цепочки дубликатов

**Выбор:** Таблица `duplicates` с полями `content_hash`, `file_path`, `duplicate_of` (ссылка на оригинал), `created_at`, `status`

**Альтернативы:**
1. Графовая структура в JSON-поле — сложная навигация
2. Множественные записи в `chunks` — дублирование метаданных

**Обоснование:** Реляционная таблица позволяет эффективно находить все версии одного документа через `WHERE duplicate_of = ?` или `WHERE content_hash = ?`.

## Risks / Trade-offs

### Риск 1: Вычисление SHA-256 для больших файлов
→ **Митигация:** Ограничение через `MAX_FILE_SIZE` (по умолчанию 100 МБ). Для файлов превышающих лимит — пропустить хеширование, использовать только путь к файлу как ключ.

### Риск 2: Конфликт имён таблиц с существующими
→ **Митигация:** Таблица `duplicates` создаётся только при первом обращении. Для PostgreSQL-бэкенда — проверка `EXISTS (SELECT 1 FROM information_schema.tables WHERE table_name = 'duplicates')`.

### Риск 3: Увеличение размера БД при частом реингесте
→ **Митигация:** Мягкое удаление + CLI-команда `duplicates cleanup` для пакетной очистки. Пользователь контролирует когда удалять.

### Риск 4: Несоответствие хеша при изменении кодировки файла
→ **Митигация:** При чтении файла для хеширования всегда использовать UTF-8. Для PDF — использовать уже распарсенный текст (после mupdf), а не бинарные данные.

### Риск 5: Производительность поиска дубликатов
→ **Митигация:** Индекс по `content_hash` в таблице `duplicates`. Для LanceDB — создание дополнительного индекса на колонку `content_hash`.

## Migration Plan

1. Создать таблицу `duplicates` при инициализации БД (LanceDB и PostgreSQL)
2. Добавить поле `status` в таблицу `chunks` (LanceDB — через addColumns, PostgreSQL — через ALTER TABLE)
3. Интегрировать хеширование в ingest pipeline
4. Добавить CLI-команды
5. Обновить документацию

## Open Questions

1. Нужно ли хранить хеш в метаданных чанков для отладки? (рекомендуется: нет, только в таблице `duplicates`)
2. Как обрабатывать случаи, когда файл был переименован, но содержимое совпадает? (считать разными документами — `file_path` уникален)
3. Нужно ли поддерживать сравнение по содержимому без пути к файлу (например, разные копии одного документа в разных папках)? (в текущей версии: нет)
